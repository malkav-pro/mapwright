## Original findings — preserved review history

### C1 — High: “document order” conflicts with the retained CPU oracle

**Plan:** §5, “One ordered program per tile” and “GPU algorithm” (lines 81–83), with R2's independent-reference parity gate.

**Evidence:** `src/Mapwright.Domain/MapModel.cs:697` stores legacy `Strokes` and resolved `TextureStrokes` in separate arrays. `Scripts/Rendering/ConnectedTerrainGraph.cs:1208` always applies all legacy texture strokes first, then all resolved texture strokes. The snapshot does not provide a unified interleaving field. Land is separately applied after pigment, and the river after Land (`ConnectedTerrainGraph.cs:935–952`).

**Failure trace:** Commit an overlapping resolved red stroke A, then a legacy blue stroke B. The existing oracle renders B then A. A compiler interpreting the plan's “original stroke/operation order” as journal chronology renders A then B. With opaque strokes, the top colour is entirely different; the ±1 channel gate cannot reconcile these contracts. “Mixed legacy/resolved” tests do not specify which order should win.

**Required revision:** Declare canonical compatibility stages explicitly: each terrain role's legacy texture array in stored order, then its resolved texture array in stored order; independent Foreground Land array in stored order; then river subtraction; then layer opacity/composition. Preserve that behavior for this redesign. Journal chronological ordering would be a separate behavior/version decision, not a compiler optimization. Define append eligibility against the canonical stage order: appending a legacy stroke cannot simply overpaint a resident result that already contains resolved strokes. Add both chronological interleavings to the proposed parity fixtures and require the existing direct oracle's result.

### C2 — High: sample filtering/chunking needs operation-specific topology and accumulation

**Plan:** §5's instruction to “Filter nonintersecting samples” and carry “partial coverage”; R2 Land/river compilation and R3 kernels.

**Evidence:** Texture coverage unions discrete dab contributions (`ConnectedTerrainGraph.cs:1235–1266`). Land is different: `LandStroke.CoverageAt` evaluates the closest point on every consecutive sample segment and takes the **maximum** footprint value (`src/Mapwright.Domain/MapModel.cs:650–663`). Land Add/Subtract is applied once per stroke to the prior mask. `LandStroke.Bounds` correctly includes segment bounds (`MapModel.cs:628–636`).

**Failure trace:** A Land stroke has endpoints at x=0 and x=1000, crossing a middle tile, with radius 10. Neither endpoint's footprint intersects that tile. Applying the texture-style sample filter removes both, although the segment covers the tile. Separately, splitting samples `[A,B,C,D]` into `[A,B]` and `[C,D]` loses segment B–C. Reusing the texture accumulator for two soft Land contributions of 0.5 yields 0.75 rather than the oracle's 0.5, even if topology survives.

**Required revision:** Specify typed operation programs. Texture programs bin discrete dabs and carry union coverage; Land programs bin segment indices, retain both endpoint records, carry maximum coverage across chunks, and apply Add/Subtract once after the stroke. Define the corresponding river segment/width-profile reducer from its reference rather than assuming texture semantics. Add the two-outside-endpoints case, a segment crossing a chunk boundary, overlapping soft Land segments, and Add/Subtract ordering to R2's direct-reference gate. These are proposed tests, not existing coverage.

### C3 — High: forced eviction and retained display generations currently prescribe incompatible reuse

**Plan:** §6 removes rendered tile state and waits for retirement before every measured edit (line 97); §7 retains the previous visible manifest and permits unchanged tile reuse (lines 108–112).

**Evidence:** The inherited harness evicts graph/history caches after commit (`Scripts/Acceptance/ConnectedAcceptance.cs:622–629`), but leaves `MapCanvas._mapTiles` alive. `MapCanvas.ShowCommittedChange` then updates dirty regions and retains other display tiles (`Scripts/App/MapCanvas.cs:230–262`). That is a distinct workload from rebuilding every visible display tile. The addendum correctly asks for both inherited and stricter modes, but does not state how front resources are treated in the stricter mode.

**Failure trace:** Generation N remains visible while “all rendered tile state” is evicted. Either its textures are actually destroyed, contradicting the old-manifest presentation/lifetime rule; or they remain alive and an implementation reuses unchanged tiles in N+1, making the claimed all-derived reconstruction partly warm. Waiting for every rendered texture's retirement cannot complete while N is intentionally retained for drawing.

**Required revision:** Define a display-only front lease as an explicit, measured eviction exception. It remains allocated and drawable until replacement, but is inaccessible as a reconstruction source. For the strict mode, prohibit copying it or including its unchanged tile handles in the new manifest; regenerate the declared visible set from preserved sources. Keep the inherited dirty-region mode separately named. Specify which retirement waits complete before the timer and which costs remain inside it, without changing the inherited timing contract. Assert the surviving resource inventory, front bytes, forbidden reuse, rebuilt tile count, and eventual retirement. Do not call this exception authoritative source data.

### C4 — High: plain FP32 can violate the hard-edge parity gate; discover that before full tool implementation

**Plan:** §5 proposes tile-relative floats and RGBA32F/R32F; R1 proves texture painting, while Land/river parity arrives in R2–R3. §3 requires ≤1 channel difference with no boundary-correlated artifacts.

**Evidence:** The direct reference computes positions and coverage predicates in doubles. Hard round texture coverage uses `distance > 1` and hard falloff (`ConnectedTerrainGraph.cs:1252–1274`). Land has exact binary predicates for hard rounds and edged polygons (`src/Mapwright.Domain/MapModel.cs:568–598`). The specification permits fractional coordinates and authoritative CPU doubles (`docs/spec.md:136`).

**Failure trace:** Choose a valid sample/centre such that a tested pixel's normalized distance is 1.00000001. The double reference excludes it. A straightforward FP32 calculation can round that distance to 1 and include it. At opacity one, the disagreement is 255 alpha/channel values, not a small floating-point discrepancy. Tile-relative coordinates reduce error but cannot remove this class of discontinuity. Polygon angle/edge classification and placed-source outside/inside predicates present analogous risks. This is a mathematical counterexample to an unconditional FP32 guarantee, not an observed failure of an implemented shader.

**Required revision:** Bring a small adversarial precision suite into R1: pixel-centred boundaries and immediately adjacent representable positions, hardness/softness zero or one, edged Land, placed-source boundaries, and 1K/4K/16K sampling. Establish the supported coordinate/recipe range. Require a proven treatment for uncertain hard-edge predicates before R2–R5: a sufficient higher-precision representation/kernel path or bounded exceptional evaluation retaining the oracle. Keep ordinary pixel work on the GPU. Do not silently replace exact edges with antialiasing or expand the error tolerance. If the chosen approach cannot preserve the existing contract, record a failed feasibility decision rather than treating the later parity failure as routine shader tuning.

### C5 — Medium: export priority and bounded counts do not yet bound global-device interference

**Plan:** §6 limits export batches and readbacks; §7 limits command bytes, operations per dispatch and staged generations; R4b requires exports not to starve interaction.

**Evidence:** `GlobalGpuBrushSurface.PaintOnRenderThread` records work on the same main RenderingDevice as canvas display (`Scripts/Rendering/GlobalGpuBrushSurface.cs:69–91`). The proposed renderer/export share that device. `docs/spec.md:31` and `docs/spec.md:187` explicitly put editing responsiveness above export speed. Existing export band assembly is sequential and bounded (`Scripts/Export/DocumentPngExport.cs`, `DocumentPngExport.ExportAsync`); its correctness does not establish GPU queue fairness.

**Failure trace:** An export scheduler finds no pending edit and records a bounded batch containing many expensive history operations. An edit arrives just afterward. Giving future interactive jobs higher priority cannot remove work already recorded ahead of them. Two readbacks bound callback/buffer concurrency, not queued compute/upload duration. Even one tile can carry a long history; a fixed operation count is not a time bound across different brushes and sources.

**Required revision:** Define the submission quantum as well as job priority: cap render-thread recording/upload time per frame, outstanding submitted work, and dispatch work estimates; yield between operation chunks and reconsider interactive work before extending the GPU queue. Measure the maximum non-preemptible chunk on the pinned machine and reduce its size when it exceeds the interaction allocation. Reserve resource capacity for an incoming interactive generation so export buffers/pages cannot hold every admissible byte. Add a proposed counterexample that injects edits immediately after the largest export admission, under dense/long history and slow PNG consumption, and checks the unchanged total latency/frame gates. It is acceptable for export to slow or pause under sustained interaction; the policy should say so.

## Strongest architecture choices

- Durable-before-GPU submission, frozen snapshots, branch-sensitive identity and a device epoch separate document authority from derived resources. Undo/new-branch and close/reopen races are correctly first-class tests.
- Pixel-owned GPU writes, separate pigment/coverage/river stages, source quantization preservation and no interactive readback address actual semantics rather than merely moving the existing upload loop.
- A real-map, commit-to-correlated-draw R1 with explicit rejection on failure is the right investment gate. The existing 211.68 ms cold-path result is not incorrectly treated as proof of a warm-cache solution.
- Shared reservations, actual retirement accounting and a single render-thread owner address allocation races that the existing check-only ledger cannot prevent.
- Evidence preservation comes before another full run. Legacy radius versus product diameter, inherited versus modern UI commands, and independently clocked versus serial load are disclosed rather than conflated.
- GPU export reuses evaluation kernels at target resolution while retaining a frozen identity, independent CPU oracle, bounded readback, cancellation and atomic publication. This is a reasonable GPU/CPU split: PNG compression, durability and bounded decoding remain CPU work.

## Original clarification requests and proof obligations

The wording below is preserved from the initial review. Items 1, 4 and 5 now have explicit architectural answers, as recorded above; implementing and proving those answers remains future work. Items 2 and 3 remain deliberate R0/R1 and engine proof gates, not unaddressed plan contradictions.

1. R0 must pin actual sampling and visibility for each row. Current `MapCanvas` starts with an 896-pixel display limit (`Scripts/App/MapCanvas.cs:20,225`); a 1920×1080 window is not itself a 4K raster workload. Preserve the original matrix and name additional 1K/4K and modern-tool workloads precisely. For resolved-only painting on a flattened import, prepare visible Land coverage or explicitly test the invisible-pigment behavior: the oracle starts coverage at zero unless legacy compatibility applies (`ConnectedTerrainGraph.cs:858–859,943–947`). A modern command correlation should not accidentally prove a no-visible-change path.
2. R0 must make the pointer/gesture versus commit-start timing decision concrete before R1. The addendum already exposes this unresolved contract; a GPU renderer cannot make release-only durable commits satisfy a per-pointer-sample durable update promise. Missing/superseded outcomes must remain reconciled with denominators.
3. Main-device write-before-draw proof, asynchronous readback ownership and safe RID retirement must be established against the actual pinned engine. The existing prototype does not prove them. A dispatch callback alone remains insufficient. The plan correctly leaves these as mandatory gates.
4. Source-page descriptors need explicit source-domain filter support and page-border addressing, including the bilinear neighbouring texels, clamping at the full raster boundary, transparency outside placed bounds and pre-composition RGBA8 quantization (`ConnectedTerrainGraph.cs:354–393,1138–1168`). Existing tile/whole tests should be supplemented by page-boundary fixtures, including a footprint requiring more than one source page. This is a detail to settle in R2, not evidence that bounded decoding has already been implemented.
5. The current resolved-texture oracle uses round falloff and a deterministic hash-based colour field (`ConnectedTerrainGraph.cs:1252–1299`), despite storing additional tip/roughness/jitter fields. State whether this redesign preserves that current behavior. Carrying fields does not prove all advertised recipe features are rendered; implementing different tip semantics while calling the old reference authoritative would introduce another incompatible goal. Do not expand this performance redesign into a silent brush-behavior change.

The focused recheck finds C1–C5 addressed in the revised architecture. It is ready to become executable plans with R1 as the go/no-go gate. Nothing in this review establishes that the existing physical acceptance threshold has been met.
