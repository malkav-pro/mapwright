# Phase 01.1 Plan 09: Production GPU Terrain and Durable-Latency Summary

**The canvas and PNG export now evaluate terrain on the GPU in IEEE double precision, pixel-equivalent to the CPU oracle, and editing sessions keep one prepared SQLite connection; the verified Phase 01.1 Full run passes every gate, with all twelve hardware rows at input-to-visible p95 16.8-21.5 ms.**

## What changed

- **Durable path.** `EditSession` applies each command once and shares the projected change (`PreparedEdit`) before the repository commit. Repository command metadata is prepared at construction, and sessions rehearse discarded, never-committed tool commands. `SqliteProjectRepository.HoldConnection()` keeps one connection for an editing or history session; every repository operation shares it in order, with re-entrant nested scopes. Per-operation connections had closed the last WAL connection on every edit, checkpointing and deleting the WAL (78-80 ms commit tails). Session preparation opens the connection and performs two no-op `user_version` rewrites, so a new WAL's first durable appends (35-48 ms after a fresh import) happen when the project opens. Commits remain `synchronous=FULL` WAL commits; the crash worker now dies while holding the connection, and fresh-process recovery passes.
- **GPU renderer.** `ConnectedGpuTerrainRenderer` runs two compute passes on the main RenderingDevice. The first resamples verified immutable sources to the canvas region (prepared canvas copy, whole-raster stretch or placed transform). The second evaluates the complete `RenderReferenceCore` composition per pixel in double precision: Background legacy then resolved strokes and opacity, then Foreground legacy then resolved strokes, base/legacy coverage, ordered Land strokes (edged polygon via fp64 `atan2`/`cos`), river subtraction and coverage x opacity, then sRGB encoding with the CPU's threshold table and banker's rounding. `MapCanvas` publishes each acknowledged revision as one texture and retires older generations after the newer one is drawn. It falls back to CPU tiles when no device exists (headless cases) or with `MAPWRIGHT_TERRAIN_RENDERER=cpu`.
- **GPU export.** `DocumentPngExport.ForProject` selects `CreateGpuCapture`: frozen sources, 512 px sub-tiles, two asynchronous readbacks in flight, and the unchanged PNG streaming, validation and atomic publication pipeline.
- **Acceptance.** The Phase 01.1 required set adds `GpuTerrainParity` and `GpuExportParity`, run windowed. `-Full` now captures the four Main/Compact shell frames into the run. For Phase 01.1, `-VerifyReport` regenerates the derived report from the saved immutable evidence and the run-bound review before verifying. Without these two runner changes, no Plan 06-era run could ever reach ten reviewed captures.
- **Icon.** The application icon uses an ivory-backed badge (`Assets/logo-icon.png`); the master artwork is unchanged.

## Deviations and residual risks

Independent verification (fresh-context agent) returned **VERIFIED WITH NOTES, no blockers**. Its notes are addressed or deferred explicitly below.

- Smoke matrices before the final run failed single rows on storage tails: 50.04 ms (first two commits of a fresh session) and 51.77 ms (a 47.5 ms first commit). These led to the prepared-session and WAL warm-up changes. A later smoke also passed a row carrying a 46.8 ms mid-run commit. Rare `FlushFileBuffers` tails on this machine can still approach the budget; the nearest-rank p95 over 15 samples is effectively the maximum, so one extreme tail would fail a row. Durability semantics were not relaxed to hide this.
- Stretched-upsampling parity is within one channel rather than byte-identical because GPU double division is not correctly rounded; placed and canvas modes are exact.
- Frame intervals during a 16K GPU export were p95 20.95 ms with 1,024 px sub-tiles. Sub-tiles are now 512 px; concurrent export-while-editing latency is not a measured Phase 01.1 gate.
- The visual review was performed by the agent at the user's request, not by a human, and is recorded per run under `artifacts/phase11-acceptance/reviews/`.
- D-09's exact 922.7294921875 x 1000 value is proven by `MapUnitPolicy.FromSource` and the synthetic import contract. The real fixture's scene is 7559.1416 x 8192 and imports as 922.7467811158798 x 1000. D-10's equal relative footprint at 1K/4K is a CPU contract (`RenderContracts`), not a connected comparison.
- The hardware harness saves percentiles and per-stage timings, not raw per-sample timestamps. The inherited UndoRedo/Cold row removes its first (cold) presentation as setup, and the recent-undo metric times `UndoAsync`/`RedoAsync` only; input-to-visible covers the visible path.
- Frame intervals were p95 23.2 ms while a 4K GPU export ran alongside a new interactive generation every frame. Export-while-editing smoothness is a follow-up, not a Phase 01.1 gate.
- **Deferred with reasons:**
  - Pointer and gesture-end tracing, and whether in-progress pointer samples must be visible within 50 ms, remain an unresolved product contract. They belong to the Phase 5 input decisions.
  - GPU device loss during export is not tested; fresh-process journal recovery stays the supported path.
  - GPU fence timestamps are not recorded; the endpoint remains `FramePostDraw`, and pixel completion is checked only outside timed runs.
  - The shared static kernels (2 shaders, 2 pipelines, 2 buffers) are not freed at process exit.
- The synchronous single-thread recording design removes the R4 late-result and epoch races by construction, because each acknowledged revision is recorded and published in one main-thread call. No race-injection tests were added.
