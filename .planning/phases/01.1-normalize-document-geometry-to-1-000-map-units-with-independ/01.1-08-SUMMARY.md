# Phase 01.1 Plan 08: Strict GPU Reconstruction Summary

**A source-bound, no-reuse real-map GPU replay was pixel-correct for 15 durable edits, but shared-kernel input-to-visible p95 was 158.373 ms against the unchanged 50 ms gate; R1 remains halted.**

## Outcome and timing boundary

`GpuTerrainStrict` is an opt-in windowed Vulkan connected case on pinned Godot 4.7.2 and an AMD RX 7800 XT. It imports the pinned real map, prepares an immutable MWDS blob, then starts each input clock **before** durable `EditSession.ExecuteAsync`, source file read/SHA verification, source upload and replay of every acknowledged stroke. Each edit uses fresh global-device source and render textures. The previous generation is kept only as a canvas display lease; it is never a compute input. The endpoint is matching revision/generation `_Draw` plus `FramePostDraw`. Independent CPU graph parity and GPU readback run outside the input clock at revisions 1, 8 and 15. The source SHA-256 is `462bcf3e1a8af948e97510ba38849d562d428d69259c43c8b58716227cfea62b`; the pinned fixture SHA-256 is `67b69858634b1a2eee8082efd80043e915dcebb36e29c8dc66e42c6406e54fab`.

The probe provides two deliberately separate kernel policies. The fresh-kernel variant recompiles shader/pipeline for every input, stricter than the architecture requires. The fairer shared-kernel variant initializes only shader/pipeline infrastructure before the run (85.6044 ms setup, including 84.9285 ms compilation); it retains **no** source or render pixels, and all per-input source work remains timed. Both retain the original durability semantics and full input-to-visible denominator.

## What the shared-kernel trial isolates

Four durable commits dominate the slow tail: sequence 1 took about 104.25 ms to commit, sequence 2 136.92 ms, sequence 7 104.86 ms and sequence 8 96.99 ms. Their full input-to-visible times were 158.373, 149.7529, 126.0641 and 116.6755 ms respectively. Those commits remain in the unchanged acceptance denominator; subtracting them would not be a pass. Sequence 13 independently took 50.4925 ms with a roughly 8.03 ms commit but **35.87 ms of replay**, showing a growing reconstruction floor even without a durable-commit outlier. GPU offload alone therefore does not solve this measured durability-plus-replay cost.

At revisions 1, 8 and 15, the shared-kernel trial changed 171,801, 255,386 and 257,565 pixels from the source respectively, with **zero** channels differing from the independent CPU reference by more than one level (maximum difference one). The fresh-kernel trial passed the same three parity checks. Shared-kernel maximum estimated GPU allocation was 91,883,008 bytes and process peak working set was 1,320,026,112 bytes versus captured budgets of 4,269,075,440 and 8,360,773,632 bytes. GPU bytes are an estimate, not complete driver-visible allocation accounting; resource lifecycle proof remains open.

- Task 1 executed and committed as `e28311f`: the strict source-bound full-replay case and optional pixel-free shared-kernel policy are implemented. The production CPU renderer remains the default. No shader, `MapCanvas` or `Main.cs` change was necessary for the strict case.

The inherited 50/100 ms input and 20/33.3 ms frame limits were not relaxed. No sequence was missing; the four shared-kernel >100 ms rows count as stalls.
- The pinned .NET build passed. The only build warnings were the pre-existing NuGet vulnerability-data network warnings. The strict connected case ran on visible Vulkan; unrelated/headless connected cases were not changed.
- Modern resolved texture with explicit Land coverage, 1K/4K/16K hard-edge precision, GPU export, complete driver-visible memory accounting and queued-draw retirement stress remain **unverified**. This is a legacy flattened-path result, not a full R1 go/no-go pass.

The fresh-kernel first run was retained as a conservative comparison, and the separately enumerated shared-kernel policy measured the permitted architecture variant.
